= Known problems

== Metabase troubleshooting

If you experience any problems when using _Stratio Discovery_, see the https://www.metabase.com/docs/v0.43/troubleshooting-guide/index.html[Metabase troubleshooting guide].

== Problem when specifying the private key for the SSL connection with PostgreSQL®

This is a Metabase bug fixed in versions 0.42.3 and later. If you have an earlier version and want to establish an SSL connection with PostgreSQL®, note that the "File Path" of "SSL Client Key (PKCS-8/DER or PKCS-12)" might not be parsed correctly, and you would have to indicate the associated configuration (`sslkey`) in the _Additional JDBC connection string options_ field. This incident does not apply if you use the _Stratio PostgreSQL Operator_ database.

== When I enter the main page, X-Ray explorations are not loaded automatically

NOTE: Fixed in version 0.50.21-0.1.X.

This minor issue is caused by the authentication layer that _Stratio Discovery_ adds to Metabase. To render the main page content, some user settings must be retrieved about whether to show x-ray suggestions (for example, there are many ways to https://www.metabase.com/docs/latest/users-guide/14-x-rays.html#disabling-x-rays[disable the x-ray feature]). Unfortunately, this `get-properties` call isn't authenticated and, due to a race condition, may execute before the calls that set a valid "metabase.SESSION" cookie after login.

Since these properties will be returned if and only if the user is trusted after checking that authentication has been completed, if the second call is executed before the first, everything will work correctly; but if it is the other way around, an `undefined` or empty value will be returned that will not be rendered on the main page.

The solution is to refresh the main page after login. Since the authentication cookie will already be written, the order of execution will no longer matter.

== Momentary appearance of the "You are not allowed to access Metabase" page on the first access to _Stratio Discovery_

This minor problem is due to the authentication layer that _Stratio Discovery_ adds to Metabase. To resolve the race condition described above, we modified the endpoint that retrieves user settings so it also authenticates users and sets the "metabase.SESSION" cookie.

During this process, if the user did not previously exist in the Metabase database, the system creates them automatically. This can create a race condition on first access, since both the settings endpoint and the authentication endpoint try to create the user simultaneously, which sometimes causes the authentication endpoint to fail.

When it fails, the browser redirects to the unauthorized access page. However, since the session cookie is already set, the application detects that the user is authenticated and redirects them back to the main Metabase page.

Although access completes without problems, the not-allowed-access page may briefly appear; this happens only on the first access to _Stratio Discovery_.

== The import of collections returns a timeout

* *Cause*: the import of large collections can sometimes return a timeout error even though the operation has been processed.
* *Solution*: even if the import service returns this error, check whether the operation has been performed correctly.

== Cache deserialization problems

Because of a security vulnerability discovered in one of Metabase's dependencies, the Metabase artifact distributed with _Stratio Discovery_ is compiled with an updated version of that dependency that no longer has that vulnerability.

This can cause problems in some cases when the Metabase cache is enabled, if one of the columns of the cached results has a type whose deserialization safety cannot be guaranteed by Metabase (this occurs, for example, with the _interval_ and _json_ types of PostgreSQL®).

No errors will be returned, but you cannot use results from the cache for this column (they will contain a map with the non-deserialized bytes "in quarantine"). Note that any user can always trigger a manual execution of the query (without using the cached data) to obtain the correct results.
