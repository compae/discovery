= Important concepts

TIP: Please read this brief guide before deploying and/or using _Stratio Discovery_.

If you understand correctly the (at first glance only) complex interaction between Metabase, _Stratio Discovery_ and the other components of the Stratio ecosystem (_Stratio {modulename}_, _Stratio PostgreSQL_…), you can:

* fine-tune the deployment,
* choose the Metabase database configuration that best suits your needs, and
* understand exactly where errors are generated.

The last step is the most important because, even following the xref:operations-guide:troubleshooting.adoc[troubleshooting guide], many of the reported problems are not due to the incorrect functioning of _Stratio Discovery_ but to the databases that it's connected to.

We're not reinventing the wheel: there's a detailed step-by-step guide provided in the https://www.metabase.com/learn/[official Metabase documentation] that will show you how to use and fine tune Metabase and its configuration.

Since Metabase is an *open source BI tool*, its goal is to *display data and not carry out actions on it*. This is why you can't carry out insertions or other write operations, and why *you only have read access to their databases*.

It's also important to remember that Metabase *won't run any queries on its own, but will depend on the drivers to connect to the database (usually via JDBC) where the query will ultimately run*.

It should now be clear that if your query takes a long time to complete, you can't blame Metabase, because it's essentially waiting for the database results to arrive.

*The database is the one doing the hard and dirty work*; Metabase just shows the results and queries in an elegant and human-friendly way, because "looks matter".

== So just what is _Stratio Discovery_?

_Stratio Discovery_ is Metabase integrated into the _Stratio_ ecosystem:

* it has added or modified security layers (for example, the _Stratio GoSec_ SSO, along with Metabase's simple default user/password authentication),
* it has added new drivers (for example, _Stratio {modulename}_, _Stratio PostgreSQL_), and
* the new CI/CD features now live independently together with Metabase in the same container (for example, the ability to export a `Y` collection from instance `A` and import it into another instance `B`, provided you've already configured the database referenced in collection `Y` in `B`).

The latest versions of _Stratio Discovery_ have a new versioning mechanism that uses the following tag syntax: `${Metabase version}-${Stratio version}`. The first version with this new label was 0.38.1-0.1. This change from the past when we used only the Stratio version is especially helpful because the new labeling lets you know immediately which version of Metabase is integrated in a _Stratio Discovery_.

CAUTION: The last version released with the old versioning mechanism (0.40.0) is *"higher"* in the lexicographic order than the latest version (0.38.1-0.2), even though the latter is actually newer. We regret the possible inconvenience that this change in the versioning mechanism may cause: it's better to make these changes that break backward compatibility but add value in the long run sooner rather than later.

== What is a driver and what is its relationship with the JDBCs?

We know that we want to connect Metabase, our application, to one or more databases. In recent decades, humanity has created a plethora of disparate systems that need to interconnect and interoperate with each other to make something useful.

Unfortunately, we create intercommunication mechanisms that are sometimes just as cumbersome and complex as communications between humans of different languages.

If you think you know how a driver and a JDBC interact, you can skip the next section and head straight to the section explaining xref:operations-guide:key-concepts.adoc#_jdbc_and_drivers_in_metabase[JDBCs and drivers in Metabase]. Otherwise, buckle up!

=== A history of intercommunication difficulties

To explain the role of drivers and `JDBCs`, we're going to have a bit of fun. Let's imagine that we're at an international summit and Metabase is speaking Spanish and our database is speaking English.

[cols=",^,"]
|===
| Spanish-speaking | No Man's Land | English-speaking

| Metabase ↔ Driver
| ↔
| JDBC ↔ Database
|===

Let's imagine that we want to execute the _sobremesa_ (after-dinner conversation) action from Metabase in our database. Metabase speaks Spanish and knows what a _sobremesa_ is, but our database would be perplexed by a literal translation (_table top_… Huh?). Even so, our database in English has all of the respective actions that make up the _sobremesa_, but it has them individually: 'make coffee after lunch', 'sit down together at the table', 'talk over coffee' and, ultimately, 'finish coffee and get up from the table'.

This means that the `Driver` (which is the Metabase translator), instead of sending the _sobremesa_ action to the `JDBC` (which is the database translator), it will group all of the individual actions and send them all together as an action because it knows that the `JDBC` can understand them.

Still, if the database had no action to 'make coffee after lunch', we would be stuck: the function we want to "translate" has to be available at the other end of the communication. This means that even if Metabase has a "filter data by user" action, if the database you're talking to doesn't have it, you can't execute that action because it's not supported… by the database!

Now let's move on to the `JDBC` and the enduring problem of correctly understanding the time and date data of different systems that have different representations for them. Metabase wants to know all the records in the database that were modified in the last twenty-four hours. But when was it 24 hours ago? _When_ does it mean "one day ago"?

The world is a big place and Metabase and the database can be configured in different time zones, and they can also represent time in different formats. Suppose Metabase uses the US format and the database uses a format with the month translated according to its local configuration. So, if we have "30-01-2021 1:00 PM" in Metabase, somehow it needs to be translated to "30-JAN-2021 13:00:00", which is the date that can be understood by the database and used for comparisons.

This exchange of information can only occur if a standard exchange format is established between the two worlds. Generally, the UTC format with ISO 8601 is used… so now both the 'JDBC' and the 'Driver' have to translate their dates to 2021-01-30T13:00:00Z.

We've now learned that the driver and the JDBC *must agree* on the format of the exchanged data! Why are we spending so much time explaining this?

=== JDBC and drivers in Metabase

While the *drivers are part of Metabase* and are community-based or developed by us in Stratio (for example, the _Stratio {modulename}_ driver), *JDBCs are usually added to the container as black boxes* and have not been developed by either our team or Metabase.

Although in some native database integrations in Metabase, the driver and JDBC functionalities can be merged into a single part, many layers are usually required for interconnection: for example, *connecting _Stratio Discovery_ to a _Stratio {modulename}_ server requires a _Stratio {modulename}_ JDBC and a _Stratio {modulename}_ driver for Metabase*.

If there's a problem executing a query because of an error generated in the database, it's clear that the culprit is the database or your query (for example, a query that refers to non-existent tables or columns).

If there's a problem executing a query because an error occurred in the JDBC, *the JDBC is usually developed by the related database, so it's not our job to correct that error*, but to integrate the new version of JDBC that contains the correction for that error.

If there's an error in one of the drivers developed by Stratio, a "translations absent" error between Metabase and a particular JDBC, it's our responsibility to correct that error. If the error lies with other drivers developed by the community, it isn't so easy to understand who should fix it, but you should inform us anyway along with the related Metabase problem, if there is one.

To understand which of these cases applies to your situation, don't just skim over the traces: study them carefully and they'll clarify it for you (or us, if you attach the traces to the ticket).

== Where does the import/export function reside?

The import/export function is essentially another program with its own Java process that runs independently of Metabase and whose endpoints are exposed outside the container so you can send HTTP requests to them.

You can report any errors or unexpected behavior (that isn't included in the xref:operations-guide:troubleshooting.adoc[troubleshooting section]) and we'll try to fix it as soon as possible.
