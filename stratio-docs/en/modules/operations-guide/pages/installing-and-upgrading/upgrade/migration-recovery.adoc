= Recovery from a migration failure

The schema migration runs during startup of the new version, so a failure results in an instance that does not become available. This page explains how the migration runs, how to determine where it left off, and what to do if it fails. To go back to the previous version, see the xref:operations-guide:installing-and-upgrading/upgrade/rollback.adoc[rollback to the previous version].

== How the migration is executed

Metabase applies the pending schema changes during its startup, before accepting requests. While it does so, the `/api/health` endpoint responds with code 503 and a body whose `status` field has the value `initializing`.

IMPORTANT: *The migration is not atomic.* Liquibase commits each schema change separately, so an interrupted migration leaves the database at an intermediate point between the two versions. No transaction rolls it back completely, so the prior backup is mandatory.

A single instance runs it: each one tries to acquire the Liquibase migration lock on the metadata database, and those that don't get it abort startup. In a PostgreSQL® database, that lock is an advisory lock tied to the session, so it disappears with the connection, and you don't need to release it manually.

== How to know at what point it was left

Two signals answer this:

* *The `databasechangelog` table of the metadata database.* Liquibase adds one row for each change it commits, so it is enough to compare its row count, or the maximum value of its `dateexecuted` column, with those of the backup.
* *The instance logs*, if you raised the _Metabase log level_ option to "INFO" before the window. With its default value, "ERROR", the migration leaves no trace.

== How to distinguish the type of failure

[cols="2,2,3", options="header"]
|===
| Symptom | Cause | What to do

| The pod restarts over and over and `/api/health` never gets past "503"
| The startup probe deadline expires before the migration finishes. The risk increases with the size of the synchronized catalog.
| Restore the backup and try again with a longer deadline, which is configured in the 'General' → 'Probes' section during the upgrade.

| The logs record "Database has migration lock; cannot run migrations." and the startup ends with "Metabase Initialization FAILED"
| The deployment has more than one replica, and another instance has taken the migration lock.
| Lower the _Instances_ option to `1` and let the instance finish the migration. Nothing needs to be repaired in the database.

| The logs record "Downgrade detected"
| A previous version has been started on a schema that has already been migrated.
| Restore the backup or go back to the new version if you did not want to roll back.

| The pod fails, and the `databasechangelog` table has not changed
| The startup fails before reaching the migration: the certificates, the configuration, or the connection with the metadata database.
| Fix the cause indicated in the logs. The database is intact, so you don't need to restore the dump.

| A schema change fails, and the log records the Liquibase error that causes it
| Preexisting data does not meet what that change requires.
| Restore the backup and consult the error with the _Stratio Discovery_ team before retrying.
|===

== After recovering

When the instance starts up again, follow the xref:operations-guide:installing-and-upgrading/verify-installation.adoc[installation verification] and return the options you changed for the window _Metabase log level_ and the startup probe deadline to their production values.
