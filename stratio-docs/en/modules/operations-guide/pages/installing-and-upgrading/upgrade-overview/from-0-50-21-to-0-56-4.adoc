= Upgrade from 0.50.21-0.2.x to 0.56.4-0.2.x

This sheet summarizes the impact of upgrading _Stratio Discovery_ from 0.50.21-0.2.x to 0.56.4-0.2.x, which accompanies the move to Universe 15.1 from 14.8.x, 14.9.x, or 14.10.x. Use it to plan the maintenance window, to know what to prepare beforehand, and what to check afterward.

Each section answers a question and links to the page that develops it. When you reach the maintenance window, follow the xref:operations-guide:installing-and-upgrading/upgrade.adoc[upgrade procedure] and the adjustments in the xref:operations-guide:installing-and-upgrading/upgrade/details-upgrade.adoc#v0564-02x[target version detailed guide].

[#summary]

== Summary

IMPORTANT: *This upgrade raises six major versions of Metabase at once, and everything underneath.* The Java version, the base image, the process supervisor, the web server, and the mechanism by which certificates are obtained all change. None of that is configurable from _Stratio Command Center_: it comes with the image. What you do have to prepare is the surrounding environment, measured in days: the platform upgraded, the backup verified, the descriptor reviewed, and the connections to data sources checked. Plan that work with <<before, Before the window>> and set the finish date.

The table answers, with one row per decision, what you need to size the window:

[cols="2,3,1", options="header"]
|===
| Question | Answer | Detail

| How much downtime is there in the worst case?
| The entire upgrade. _Stratio Discovery_ does not support high availability, so the service becomes unavailable from the moment the version is changed until the new pod responds. Usually, this takes *a few minutes* (estimated). The startup probe deadline (300 seconds by default) doesn't cap it: when it expires, Kubernetes restarts the pod and the migration is left halfway, so the backup has to be restored and the migration retried.
| <<outage, Downtime>>

| What does that duration depend on?
| On the number of rows of the tables that the migration rewrites, which are those of metadata for fields, questions, and dashboards, not on the total size of the database: the execution and view history, which is the one that grows with use, only receives structural changes. There is no published measurement.
| <<data, Data>>

| How long does the maintenance window last in total?
| The service restart, with the internal migration, plus the closing checks. With a half-hour margin, there is room for both (estimated).
| <<phases, Steps>>

| Can the work be divided into several windows?
| *Partially.* The platform upgrade, the backup, and the descriptor review are performed in previously established time windows. The version change itself is a single continuous window.
| <<before, Before the window>>

| Does something stop working until another module is upgraded?
| *No, but there is a mandatory order.* _Stratio KEOS_ must already be on the target Universe, because its Vault injector is what delivers the certificates. No other module blocks: the _Stratio {modulename}_ servers only need to be 0.11.0 or higher, and the source Universe already meets that minimum.
| <<modules, Modules>>

| Does the data model change and is a backup needed?
| *Yes* to both. Metabase applies schema migrations on first startup of the new version, and backing up the metadata database is mandatory because it is the only way to revert.
| <<data, Data>>

| Can you go back at any time?
| *Only until the first schema change is committed.* If the startup fails before the migration, it is enough to revert to the previous version; afterward, going back involves restoring the backup and losing what was created after the upgrade.
| <<rollback, Rollback>>

| Does the previous version work on Universe 15.1?
| *No.* It is not validated: each Universe declares the _Stratio Discovery_ version that has been tested with it, and 0.50.21-0.2.x is not part of Universe 15.1.
| <<coexistence, Coexistence>>

| What is the global risk?
| *High.* There is no high availability or automatic rollback; the migration runs with a per-attempt deadline set by the startup probe and does not resume if it is interrupted. In addition, the jump changes the Java version, the base image, and the secrets retrieval mechanism at the same time.
| <<known-issues, Known warnings and incidents>>
|===

.Message to communicate
[caption=]
====
_Stratio Discovery_ raises six versions of Metabase in a single operation. During the upgrade, the service is not available. The outage duration has not been measured and depends on the volume of stored questions and dashboards; what is set is the ceiling, because the platform restarts the instance if startup exceeds five minutes. In-progress queries and open sessions are lost, and the subscriptions scheduled during the downtime are not sent. Plan the window with margin and warn users so they don't launch long queries just before it opens.
====

[#scope]

== Scope of the upgrade

The three source Universes have the same version of _Stratio Discovery_, 0.50.21-0.2.0, so this sheet applies without changes to 14.8.x, 14.9.x, and 14.10.x, and the procedure is the same in all three.

If your instance is on a version prior to 0.50.21-0.2.x, first review the xref:operations-guide:installing-and-upgrading/upgrade/special-upgrades.adoc[special upgrades], because the considerations of the intermediate versions apply in full to the direct route.

[#components]

=== Components and upgrade order

_Stratio Discovery_ is deployed as *a single container* and is upgraded in a single operation: there is no internal order to respect. Inside, three supervised processes coexist, which start at the same time and without declared dependencies between them:

[cols="1,2,2,3", options="header"]
|===
| # | Process | Where it stores state | Why it does not need its own window

| 1
| nginx
| It does not store state. Terminates TLS and exposes the health endpoint.
| It starts with the container, and its configuration is regenerated on each startup from environment variables.

| 2
| Metabase
| In the metadata database of _Stratio PostgreSQL Operator_. It is the only persistent state of the service.
| It runs the schema migration on startup, before responding on the health endpoint.

| 3
| Export and import service (`discovery-cicd`)
| It does not store state. It delegates authentication and data to Metabase.
| It shares the container and the lifecycle with the previous ones.
|===

NOTE: The instance does not store files: the descriptor declares no volumes, and everything the container writes on each startup (certificates, generated configuration, and the JAR files downloaded through the _Extra JARs to add to Metabase plugins folder_ option) is regenerated automatically. The only relevant backup is that of the metadata database.

[#modules]

=== Relationship with other modules

_Stratio Discovery_ shares the upgrade calendar with the following modules. Both directions matter, because the second is what determines the order in which the platform is upgraded:

[cols="2,2,4,4", options="header"]
|===
| Related module | What relationship there is | When _Stratio Discovery_ is upgraded | When the related module is upgraded

| _Stratio KEOS_
| The platform on which the service runs. Its `oauth2proxy` authenticates all requests, and its Vault injector delivers the certificates and the public key used to validate JWT tokens.
| No impact on the platform. The new version obtains its certificates and the public key from the Vault injector, whose annotations the Universe 15.1 descriptor adds, so the platform must be on that Universe before changing the version.
| Upgrade the platform first in its own window. It is the only module with a mandatory order.

| _Stratio {modulename}_
| It provides the catalog and data that the questions query through a Metabase-specific driver and its JDBC driver.
| The JDBC driver included in the image goes up from version 2.32.x to 4.x. The servers must be 0.11.0 or higher, which the source Universe already meets.
| None on the upgrade process, but yes on the existing questions: if _Stratio {modulename}_ also goes up from the 0.11.x line to 1.1.x with the Universe, its SQL syntax changes. Review the native questions that use `mask` (now `xdmask`), `TIMESTAMPADD`, or `TIMESTAMPDIFF`, according to the _Stratio {modulename}_ documentation for the target Universe.

| _Stratio Gosec_
| It provides identities, the groups that feed the allowed groups list, and access policies for the metadata database.
| No impact: creating the user and policies works the same on both versions.
| No impact, provided the groups in _Allowed groups_ and _Admin group_ keep their names.

| _Stratio PostgreSQL Operator_
| It stores the metadata database, which the service connects to through mutual TLS, normally through PgBouncer.
| No impact on the database beyond the schema migration that Metabase runs.
| _Stratio Discovery_ becomes unavailable while the database is not responding. Chain the two windows or separate them completely.

| _Stratio Command Center_
| It deploys, configures, and upgrades the instance, and it is where the version is changed.
| No impact. The Universe 15.1 descriptor requests the new fields during the upgrade.
| No impact on _Stratio Discovery_.
|===

Upgrade the modules in this order: _Stratio KEOS_ first, in its own window, and then _Stratio Discovery_. The rest of the modules do not impose any order: you just have to avoid their windows overlapping with that of _Stratio Discovery_, because a database or a catalog that does not respond during verification is confused with an upgrade failure.

[#coexistence]

=== Version coexistence

[cols="2,1,3", options="header"]
|===
| Scenario | Supported? | Limitations

| The previous _Stratio Discovery_ version on Universe 15.1
| No
| Each Universe declares the _Stratio Discovery_ version tested with it, and 0.50.21-0.2.x is not part of Universe 15.1. The new version depends on the new platform because it gets its certificates from the Universe 15.1 Vault injector.

| The upgraded module with its consumers still not upgraded
| Partially
| The integrations that call the Metabase API continue to work with the "metabase.SESSION" cookie. Review the ones that export and import collections: the service does not support some Metabase functionality, both before and after the upgrade.

| Two _Stratio Discovery_ instances on different versions
| Yes, if they do not share a database
| Each instance uses its own metadata database, so two instances on different versions coexist without interfering with each other. What is not supported is pointing two different versions to the same database: the first one to start migrates the schema, and the other stops recognizing it.

| Several replicas of the same instance
| No
| The descriptor declares the service without high availability and with a single replica. No leader election or shared session state exists, so the pause during the upgrade is inevitable.
|===

[#phases]

=== Steps from beginning to end

_Stratio Discovery_ has no controlled upgrade process: there is nothing to start or finish from an API, nor is there an upgrade state to check. The sequence consists of changing the version in _Stratio Command Center_, following the xref:operations-guide:installing-and-upgrading/upgrade.adoc#cct-steps[steps of the upgrade procedure], and waiting for the instance to become available again.

[cols="4%,17%,49%,30%", options="header"]
|===
| # | Step | What happens and what stops working | Duration and downtime

| 1
| Preparation
| Everything indicated in <<before, Before the window>>. Nothing stops working.
| Days or weeks (estimated). No downtime.

| 2
| Notice and drain
| Notify users not to launch long queries or catalog synchronizations. No mechanism drains in-progress work, so this step is organizational. Nothing stops working.
| A few minutes (estimated). No downtime.

| 3
| Version change
| Update of the service version in _Stratio Command Center_, which recreates the deployment with the new image. Everything stops working.
| A few minutes (estimated). Total.

| 4
| Startup and migration
| The container prepares the configuration, obtains the certificates from the Vault injector, and starts the three processes. Metabase applies the 175 schema changes that separate Metabase 0.50.21 from 0.56.4 and responds on the health endpoint with "503" until it finishes. Everything stops working.
| A few minutes (estimated), with a 300-second deadline per startup probe attempt. Total, throughout the entire step.

| 5
| Verification
| The <<checks, Post-upgrade checks>>. Nothing stops working.
| The time the six checks take you (estimated). No downtime.
|===

How to verify that each step has finished correctly:

. *Preparation:* all the rows of <<before, Before the window>> are covered.
. *Notice and drain:* no long query or catalog synchronization is left in progress.
. *Version change:* _Stratio Command Center_ reports the new version, and the previous pod has disappeared.
. *Startup and migration:* the pod becomes _Ready_, that is, the `/api/health` endpoint responds. Meanwhile, the instance logs only report progress if you have configured the _Metabase log level_ option to "INFO".
. *Verification:* all the closing checks pass.

IMPORTANT: *The startup probe deadline caps each attempt, not the downtime.* It is obtained by multiplying the _Startup probe periodSeconds_ and _Startup probe failureThreshold_ options of the 'General' → 'Probes' section, which by default are 5 and 60, respectively; that is, 300 seconds. The duration grows with the size of the synchronized catalog, not the volume of data queried, because several changes rewrite `metabase_field` and `metabase_table` row by row. If the deadline expires, Kubernetes restarts the pod, and the migration stops at the last committed change. The next startup would resume the pending changes, but Metabase doesn't consider an interrupted migration a state: restore the backup and try again with a longer deadline.

[#data]

=== Data and consistency

* *What changes in the data model.* The metadata database schema moves from Metabase 0.50.21 to Metabase 0.56.4: 175 cumulative changes that Metabase applies through Liquibase during the first startup of the new version. Most are structural changes, but some rewrite existing content, and that is why the backup is mandatory. The two triggers that _Stratio Discovery_ adds to the dashboard subscriptions do not change.
* *Is a mandatory backup needed beforehand?* Yes, of the metadata database and the deployment descriptor. There is no other way to revert once the migration has been applied. The instance does not store files, so there is nothing else to copy.
* *What to do if the migration fails halfway through the process.* The database is left half-migrated, so the path is always the same: scale the instance to 0, restore the metadata database dump, fix the cause indicated by the logs (or extend the startup probe deadline if that is what expired), and scale back to 1 replica. Do not try again without restoring.
* *Can the data be left in an intermediate state?* Yes, and that is why the backup is mandatory. Liquibase commits each schema change separately, so an interrupted migration leaves the database at an intermediate point between the two versions: neither complete for the new one nor valid for the previous one.
* *How to verify that the data is correct after the migration.* The instance responds on `/api/health`; the interface reports the new version and the existing collections, questions, and dashboards open and execute. During migration, that same endpoint responds with code "503" and a body whose `status` field is `initializing`, allowing you to distinguish an in-progress migration from a failed startup.

[#no-return]

=== Point of no return

* *What it is.* The first schema change that Metabase commits when starting the new version. No prior state confirms or cancels the operation: the migration runs on its own as part of startup, and each change is committed as soon as it finishes.
* *How to know that it has been passed.* The pod becomes _Ready_, and the interface reports the new version. But it is enough for the startup to have reached the migration: if it fails afterward, the point of no return has already been passed, even if the instance does not become available.
* *What stops being possible from that point on.* Going back to the previous version without restoring the backup. Metabase checks the schema version before migrating and refuses to start if there is a more recent version than its own, showing the error "Downgrade detected".

[#outage]

=== Downtime and availability

* *What has been done to reduce it.* The xref:operations-guide:installing-and-upgrading/upgrade.adoc#downtime[downtime and availability] is detailed in the upgrade procedure. The preparation, the platform upgrade, and the descriptor review are performed outside the window. Within the window, nothing can be brought forward: the migration is part of startup.
* *What cannot be avoided and why.* Complete downtime. Metabase does not support progressive upgrades between major versions: the migration acquires a lock on the metadata database from a single instance, and the schema changes it applies break any instance that is still running the previous version. That is why the descriptor declares the service without high availability and with a single replica, and why there is no way to keep the previous version in service while the new one migrates.
* *Stop and startup order.* There is no order to decide: _Stratio Command Center_ recreates the deployment, and the container starts up its three processes at the same time. nginx can accept connections before Metabase is ready, so a gateway error during startup is expected and does not indicate a failure.
* *Who is warned and with how much notice.* Announce the estimated range and what stops being available, following the change management policy of each environment. _Stratio Discovery_ does not impose any notice deadline.
* *Recommendation to plan the window.* Size it with the startup probe deadline plus the time of the closing checks, and communicate a range, not an exact figure. Rehearse beforehand, in preproduction, with a representative volume of data; it is the only way to estimate the actual migration duration.

[#work-in-flight]

=== Work in progress during the window

_Stratio Discovery_ does not drain the in-progress work before stopping: the instance is replaced and whatever was running is lost. This table summarizes what happens to each thing and how it recovers:

[cols="2,4,2,4", options="header"]
|===
| What may be running | What happens to it | What to do beforehand | How it recovers afterwards

| Queries in execution
| They fail as soon as the instance stops responding. The query is lost, and you can simply launch it again: a query does not modify the source data.
| Warn users not to launch long queries.
| Launch them again from the interface.

| Open user sessions
| They end. Users must re-authenticate through the _Stratio KEOS_ `oauth2proxy`.
| Nothing
| Users log in again. The previous session is not recovered.

| Catalog synchronizations in progress
| They are interrupted. A partial synchronization leaves tables or fields unregistered, but does not corrupt the metadata database.
| Avoid launching a full synchronization just before the window.
| Launch the synchronization again from the database configuration.

| Scheduled dashboard subscriptions
| Subscriptions scheduled during the downtime are not sent and are not recovered afterward.
| Check which subscriptions fall within the window and warn their recipients.
| Manually send those that cannot wait for the next cycle.

| Metabase API calls and external integrations
| They fail while the service is not available.
| Pause the external orchestration during the window to prevent failed attempts from accumulating.
| Relaunch the affected flows from the orchestrator.

| Collection exports and imports in progress
| They fail. An interrupted import can leave the collection half-created at the destination.
| Do not launch imports during the window.
| Review the destination collection and import it again if it was left incomplete.
|===

[#post-upgrade]

== After the upgrade

[#regressions]

=== Regressions to expect

Coming from 0.50.21-0.2.x, the changes of versions 0.56.4-0.1.x and 0.56.4-0.2.x arrive at the same time. None of these regressions prevents the instance from starting up, but they do affect specific functionalities. They are grouped by priority, according to when action is required:

* *Blocking or requiring mandatory action before the window*: authentication if the deployment does not use `gosec-sso`, the removed or renamed deployment options, and the data sources whose driver is no longer included.
* *Requiring action after the upgrade*: variables that stop being injected and default values that change.
* *Behavior changes to keep in mind*: what continues to work but in a different way.

==== Blocking or requiring mandatory action before the window

[cols="1,1,2,1", options="header"]
|===
| What stops working or changes | Cause | How to resolve it | In the meantime

| The Amazon Athena connections
| Its driver was removed from the image because it dragged along dependencies with vulnerabilities.
| Inventory those connections before upgrading and decide on an alternative: publishing that data through _Stratio {modulename}_ or providing the driver through the _Extra JARs to add to Metabase plugins folder_ deployment option.
| The questions and dashboards that use them are preserved, but cannot be executed.

| The _Skip Metabase's Statement final cancellation in Virtualizer driver_ deployment option (`VIRTUALIZER_DRIVER_SKIP_STMT_CANCELLATION` environment variable)
| The option was removed from the descriptor. It avoided blocking JDBC connections to _Stratio {modulename}_ servers before version 0.11.0.
| No action is needed if you come from Universe 14.8, 14.9, or 14.10: the _Stratio {modulename}_ version of those Universes is already above the minimum. Check the version before the window.
| If any server were below 0.11.0, its JDBC connections would be blocked.

| The "Enable OAUTH", "SSO external URI", "SSO internal URI", and "Dynamic authentication" deployment options
| Authentication moved completely to the _Stratio KEOS_ `oauth2proxy`, which issues the cookie with the JWT token; the instance validates it with the public key that the ingress publishes and that the Vault injector delivers to it. The instance no longer needs to know the SSO address.
| No action is needed on the instance: the Universe 15.1 descriptor no longer requests those fields. Review any of your own automation that sets them.
| The values you had configured are ignored.

| The auditing of the content of the API responses
| The internal web server moved from OpenResty to nginx, and with it the module that recorded the AES-encrypted response body disappeared. The `LOG_ACCESS_DATA`, `DATA_AUDIT_ENCRYPTION_KEY_PASS`, `DATA_AUDIT_ENCRYPTION_IV_PASS`, `EXTRA_NGINX_LOG_PROPERTIES`, and `EMBED_TOKEN_USER_CLAIM` variables go with it. None of them were in the descriptor, so it only affects deployments that set them manually.
| There is no replacement in the product. If your environment depends on that auditing, raise the requirement before upgrading. The normal nginx access log, with the user resolved, remains the same.
| The data audit lines stop being generated, without warning.

| The keystore and truststore passwords
| Previously, they were stored in Vault and were stable; now the container generates them randomly on each startup because the Vault injector delivers the certificates. The `SecretsBundle` no longer creates the keystore password.
| Review any integration that opens _/etc/pki/discovery.jks_ or _/etc/pki/ca-bundle.jks_ with a fixed password. Inside the container, they are still available as environment variables.
| The integration that used the previous password can no longer open the store.

| JAR files of own or third-party drivers
| Metabase redid its internal driver API between 0.51 and 0.56: functionalities were removed, namespaces were moved, and the signatures of the synchronization methods changed.
| Recompile each driver against the Metabase 0.56 API and test it with Java 21 before the window. Those provided through _Extra JARs to add to Metabase plugins folder_ are not validated on deployment.
| The driver does not load, and the databases that depend on it become inaccessible.

| The `USE_GOSEC_SSO_AUTH` environment variable in legacy deployments
| It no longer exists, along with the startup file that interpreted it. In the previous version, it forced the authentication method to `gosec-sso` and warned that this was deprecated. The _Authentication method_ option still offers the same four values, but now redirects to the advanced configuration.
| Check the authentication method in the current descriptor and set it explicitly before upgrading, instead of relying on the forcing that no longer exists.
| The variable produces no effect or warning.

| The integrations that read the cookie name from the descriptor
| The "OAuth2 cookie name" option is renamed to _oauth2proxy cookie name_ because the cookie is issued by `oauth2proxy`, not the SSO, and the environment variable it exposes changes.
| Rename the variable in any automation that reads it inside the container: it changes from `OAUTH2_COOKIE_NAME` to `JWT_COOKIE_NAME`. The default value does not change: it is still `stratio-cookie`.
| The automation that reads the old name does not find the variable.
|===

==== Requiring action after the upgrade

[cols="1,1,2,1", options="header"]
|===
| What stops working or changes | Cause | How to resolve it | In the meantime

| The environment variables of the probes, the resource ones (_Instances_, _CPUs Request_, _Memory request (MB)_, their types, and their limits), and the database creation and discovery ones stop being injected into the container
| Their options remain in the descriptor and are applied to the deployment, but they no longer propagate as environment variables inside the container. The database connection ones (`MB_DB_URL`, `MB_DB_USER`, `MB_DB_SSL`…) and `MEMORY` are not affected.
| Review any of your own processes that read them from inside the container and get that data from the descriptor or from the Kubernetes API.
| The process that reads them receives an empty value.

| The middleware log level decreases in detail
| The default value of the _Middleware log level_ option changes from "DEBUG" to "INFO".
| If you depended on those traces, set the value back to "DEBUG" in the 'General' → 'Log levels' section of _Stratio Command Center_.
| The "DEBUG"-level messages of that layer stop appearing in the logs.

| The format of the logs sent to the centralized log platform
| The selector that let through raw the messages that were already JSON depended on the Java 8 scripting engine, which Java 21 does not include. Now all messages are emitted with the same pattern: the escaped text inside the `@message` field.
| Review the parsing rules of your log platform or your SIEM if they depend on receiving the original JSON unwrapped.
| The lines continue to arrive, but with a different structure than before.

| The download options for external JAR files
| The download moved from `wget` to `curl`, so the `WGET_CUSTOM_SECURITY_OPTS` variable is now called `CURL_CUSTOM_SECURITY_OPTS` and its default value stops being empty: it uses the instance's certificates.
| Rewrite in `curl` syntax the options that you will pass manually. `EXTRA_JARS` does not change.
| The old options are ignored, and the download may fail because it lacks credentials.

| The legacy compatibility environment variables
| They disappear along with the startup file that interpreted them: `TENANT_NAME` (alias of `DISCOVERY_INSTANCE_NAME`), `SECRET_NAME`, `OAUTH_COOKIE_PREFIX`, and `JWT_VALIDATION_DISABLED`.
| Replace `TENANT_NAME` with `DISCOVERY_INSTANCE_NAME`. The other three have no replacement because that functionality no longer exists.
| The variables are ignored without any warning.

| The Java Virtual Machine options added manually
| The image moves from Java 11 to Java 21.
| Review and retest the customized options. Java 21 silently ignores options it doesn't recognize.
| The customized configuration may not be applied without any warning.
|===

==== Behavior changes to keep in mind

[cols="1,1,2,1", options="header"]
|===
| What stops working or changes | Cause | How to resolve it | In the meantime

| The export and import of collections that use actions, models created from CSV files, timelines, or alerts
| The export and import service does not support those functionalities. This is not a regression from this upgrade: it already occurred in the source version and remains.
| Avoid those functionalities in the collections promoted between environments, or promote them manually.

[#checks]

=== Post-upgrade checks

Close the window when the instance responds on `/api/health`, _Stratio Command Center_ reports the new version, and the following checks pass, as indicated by the xref:operations-guide:installing-and-upgrading/upgrade.adoc#post-check[post-check] of the procedure. The xref:operations-guide:installing-and-upgrading/verify-installation.adoc[installation verification guide] covers the interface access and the launch of a question:

. Login works, and a user from an allowed group accesses the application.
. A user from the administration group has administration permissions, which confirms that group synchronization with _Stratio Gosec_ continues to work.
. A question against a _Stratio {modulename}_ database returns results.
. A question against a _Stratio PostgreSQL Operator_ database returns results.
. The catalog synchronization of a database finishes without errors.
. A test collection exports and imports correctly.

These tasks remain pending after the window. There is no fixed deadline: what matters is what does not work until each one is done.

[cols="2,3,2", options="header"]
|===
| Task | What must be done | What does not work until it is done

| Return to their production value the startup probe deadline and the _Metabase log level_ option, if you changed them for the migration
| Return the values of the 'General' → 'Probes' section to those you had before opening the window.
| Nothing in normal operation: the deadline only affects the time Kubernetes waits on subsequent startups.

| Resolve the <<regressions, regressions>> that apply to you
| Rename the variables in your automations, review the Java virtual machine options, and decide what to do with the data sources whose driver is no longer included.
| Those automations and those data sources.

| Review the dashboard subscriptions that were not sent
| Check which ones fall within the window and send them manually if they cannot wait for the next cycle.
| Their recipients do not receive the send corresponding to the window.

| Relaunch the interrupted catalog synchronizations
| Launch the synchronization from the configuration of each affected database.
| The tables or fields created during the window do not appear when creating questions.
|===

[#problems]

== If something goes wrong

[#rollback]

=== Rollback

The upgrade procedure summarizes what to do if the xref:operations-guide:installing-and-upgrading/upgrade.adoc#upgrade-failure[upgrade does not go well], and this section details it. There is no automatic rollback beyond the <<no-return, point of no return>>, and *reverting the version in _Stratio Command Center_ is not enough once the migration has started*: Metabase refuses to start on a schema newer than its own. Metabase offers a command to downgrade the schema, but it only rolls back one major version, and there are six between 0.50.21 and 0.56.4, so this route doesn't work. What to do depends on whether the migration has started, and both cases are detailed in the xref:operations-guide:installing-and-upgrading/upgrade/rollback.adoc[rollback to the previous version].

[cols="2,1,4,2", options="header"]
|===
| Moment of the process | Possible? | What is done | How long it takes and if data is lost

| The upgrade is aborted before changing the version, in steps 1 or 2
| Yes
| Nothing: the deployment has not been modified. Resume the preparation when you decide on a new date.
| Immediate (estimated). No data is lost.

| The version has been changed, but the startup fails before reaching the migration
| Yes
| Revert the service version in _Stratio Command Center_. The database has not been touched, so there is no need to restore the dump. This applies if the failure occurs while preparing certificates or during configuration.
| A few minutes (estimated). No data is lost.

| The migration has started, whether it has been completed or not
| Yes, only by restoring
| Revert the service version, restore the metadata database dump, and, if you changed the descriptor, also restore its copy. There is no shortcut: even if the migration was left halfway, the schema is no longer valid for the previous version.
| Depends on the backup size (estimated). Yes: everything created after the upgrade is lost.
|===

WARNING: Restoring the dump returns the database to the state in which it was at the time of the backup. Everything created or modified afterward (questions, dashboards, collections, subscriptions, and database connections) is lost, including edits made during the window itself.

While step 4 runs, the `/api/health` endpoint distinguishes between an in-progress migration and a failed startup, and the instance logs record the start and end of the migration, provided you have configured the _Metabase log level_ option to "INFO". If the pod restarts, check those logs or, by comparing the `databasechangelog` table of the metadata database with the backup, whether any change was applied, and apply the <<rollback, rollback>>: do not try again on a database in the middle of the migration. You don't need to release any lock manually: the lock is released automatically when the process ends or dies. To identify the type of failure, see the xref:operations-guide:installing-and-upgrading/upgrade/migration-recovery.adoc[recovery from a migration failure]; for the rest of the incidents, see the xref:operations-guide:troubleshooting.adoc[troubleshooting guide].
